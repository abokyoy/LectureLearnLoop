## P001 — Git clone 代理超时失败

**日期**：2026-09-27  
**分类**：环境  
**严重程度**：高（完全阻止代码获取）

### 问题描述
执行 `git clone https://github.com/abokyoy/LectureLearnLoop.git` 时失败。

### 错误现象
```
fatal: unable to access 'https://github.com/...': 
Failed to connect to 127.0.0.1 port 10808 after 2168 ms: Couldn't connect to server
```

### 根本原因
Git 全局配置了代理：
```bash
git config --global http.proxy http://127.0.0.1:10808
git config --global https.proxy http://127.0.0.1:10808
```
但代理服务（端口 10808）未在本机运行，导致连接被拒绝。

### 解决方式
通过 `-c` 参数临时覆盖配置，绕过代理：
```bash
git -c http.proxy='' -c https.proxy='' clone https://github.com/abokyoy/LectureLearnLoop.git
```

### 规避建议
1. **首选方案**：每次 git 命令都带 `-c http.proxy='' -c https.proxy=''` 参数（代理未运行时）；若 V2RAYN 在运行，可直接用 `-c http.proxy=http://127.0.0.1:10808` 走代理
2. **永久方案**（需用户授权）：`git config --global --unset http.proxy` 删除全局代理配置
3. **检测方式**：执行前先检查 `git config --global --list | Select-String proxy`，发现代理配置时主动提示

### 后续更新（2026-09-27）
用户确认本机装有 **V2RAYN** 代理软件（127.0.0.1:10808），用于访问外网。已验证通过该代理访问 `stitch.googleapis.com` 返回 HTTP 405（网络层可达，端点只接受 POST）。
**代理是否生效取决于 V2RAYN 客户端是否在运行**，每次外网请求前若失败先确认客户端状态。网络走向规则详见 `AGENTS.md` 第十一节。

**故障恢复**：若系统因网络问题卡住/反复超时，重启 V2RAYN 工具：
- 工具路径：`C:\Users\Administrator\Desktop\v2rayN.exe`
- 重启方式：`Stop-Process -Name v2rayN -Force` 后重新启动该 exe，等几秒后再验证连通性

## P002 — Flask SECRET_KEY 每次重启失效（已知，待修复）

**日期**：2026-09-27  
**分类**：后端  
**严重程度**：中（每次重启 Flask 服务后，用户 session 失效，需重新登录）

### 问题描述
`app_flask.py` 第 34 行：
```python
app.config['SECRET_KEY'] = os.urandom(24)
```
每次服务重启，`SECRET_KEY` 随机变化，导致所有已签名的 session cookie 失效。

### 解决方式（待实施）
改为固定密钥文件：
```python
# 启动时读取或生成并持久化
def get_or_create_secret_key():
    key_file = os.path.join(app.root_path, '.flask_secret_key')
    if os.path.exists(key_file):
        with open(key_file, 'rb') as f:
            return f.read()
    key = os.urandom(24)
    with open(key_file, 'wb') as f:
        f.write(key)
    return key

app.config['SECRET_KEY'] = get_or_create_secret_key()
```

### 规避建议
- 在 `.gitignore` 中确保 `.flask_secret_key` 不被提交

## P003 — 文件路径安全检查可被 `..` 绕过（已知，待修复）

**日期**：2026-09-27  
**分类**：安全  
**严重程度**：高（可读取任意文件）

### 问题描述
`app_flask.py` L321-328 的路径安全检查：
```python
base_dir = os.path.join(app.root_path, 'data')
full_path = os.path.join(base_dir, file_path)
if not full_path.startswith(base_dir):
    return 403
```

### 攻击场景
`file_path = "../config.py"` → `full_path` = `项目根/config.py`  
`startswith(base_dir)` 检查可能因 Windows 路径格式差异（`/` vs `\`）而绕过。

### 正确方式（待实施）
```python
import os
base_dir = os.path.realpath(os.path.join(app.root_path, 'data'))
full_path = os.path.realpath(os.path.join(base_dir, file_path))
if os.path.commonpath([base_dir, full_path]) != base_dir:
    return 403
```

### 规避建议
- 涉及文件路径操作时，**始终用 `os.path.realpath` 解析后再比对**，不用 `startswith`

## P004 — 两套练习数据库功能重叠（已知，待收敛）

**日期**：2026-09-27  
**分类**：架构  
**严重程度**：中（数据不一致风险）

### 问题描述
当前存在两套独立的练习数据存储：
- `dal/practice_dao.py` → 使用 `practice_history.db`
- `services/practice_service.py` → 使用 `practice_data.db`

两者功能高度重叠，但各自维护独立数据库，会导致：
1. 通过 Service 保存的练习记录，DAO 层读取不到（反之亦然）
2. 统计计算基于不同数据源，结果不一致

### 收敛方向
合并为单一数据库，统一走 Service → DAO 的分层路径，不允许 Service 和 DAO 各连各的库。

### 规避建议
- 在数据库路径统一修改前，所有新功能只引用其中一套（`practice_history.db` 优先，因为建表 SQL 更完整）

## P006 — Flask 开发模式 debug=True 暴露到局域网

**日期**：2026-09-27  
**分类**：安全  
**严重程度**：高（Werkzeug 调试器支持远程代码执行）

### 问题描述
`app_flask.py` 最后启动代码：
```python
app.run(debug=True, host='0.0.0.0', port=5000, threaded=True)
```
`debug=True` 开启 Werkzeug 交互式调试器，`host='0.0.0.0'` 监听所有网络接口。
局域网内的任意设备可以访问 `http://本机IP:5000`，调试器可执行任意 Python 代码。

### 解决方式（待实施）
开发完成后，改为：
```python
app.run(
    debug=False,        # 关闭调试器
    host='127.0.0.1',   # 只监听本地
    port=5000,
    threaded=True
)
# 生产环境应使用 gunicorn，不用 Werkzeug
```

### 规避建议
- **开发过程中** 如确需 `debug=True`，应将 `host` 改为 `127.0.0.1`
- 在交付前必须检查 `debug=True` + `0.0.0.0` 组合是否已移除

## P007 — Deepgram language=multi 对中文音频返回空转写

**日期**：2026-09-28  
**分类**：外部服务  
**严重程度**：高（中文课程场景功能失效且无任何报错）

### 问题描述
P6 验收上传中文 YouTube 视频音频（16k mono WAV，能量峰值 31065 排除静音）到 Deepgram，HTTP 200 但 transcript 长度为 0，`confidence=0.0`。

### 排查过程（对照实验法）
同模型同参数三组对照（`server/tests/p6_dg_ab.py`）：
- 英文音频 + `language=multi` → 1176 字 ✓
- 中文音频 + `language=zh-CN` → 775 字 ✓
- 中文音频 + `language=multi`（含 detect_language）→ **0 字** ✗

结论：nova-2 的 multi 语言包实际不覆盖该中文音频；空结果不报错，极易误判为“音频没声音/上传失败”。

### 解决方式
1. 服务端 `/api/asr/config` 默认下发 `zh-CN`（`config.DEEPGRAM_LANGUAGE`，.env 可改）；支持 `?language=` 参数，旧设置页键位 auto/zh/en 自动归一化，非法语言 400
2. 悬浮窗增加语言下拉（中文默认/英文/多语言）
3. 测试脚本环境变量可覆盖（`P6_DG_LANG`），英文回归用例显式传 `multi`

### 规避建议
- 接入任何 ASR/LLM 外部服务时，**“成功但结果为空”必须作为独立失败分支断言**（长度>阈值而不只是 status==200）
- 换语言/换模型先跑最小对照脚本再改产品代码

## P008 — yt-dlp 下载 YouTube 遇 bot check / 合并容器音轨

**日期**：2026-09-28  
**分类**：外部服务  
**严重程度**：中（验收素材获取链路受阻）

### 问题描述与解决
1. 默认下载报 “Sign in to confirm you're not a bot” → 绕过：`--js-runtimes node --extractor-args "youtube:player_client=tv_embedded,android,web_safari"`（本机以 Node 作 JS 运行时）
2. 绕过后仅剩 format 18 合并流（mp4 含 H.264+AAC），Deepgram 对合并容器直接返回空 → 必须 ffmpeg 抽轨：`-vn -ac 1 -ar 16000 -c:a pcm_s16le in.mp4 out.wav`
3. Deepgram 同步预录接口对长音频（10 分钟）结果不稳定 → 裁前 240s 送检足够验收
4. auto-subs 对该视频不可用，字幕路线不能作依赖

### 规避建议
- 视频站点音频一律“抽轨成 16k 单声道 WAV”后再送 ASR，不直接传视频容器
- 用 glob 选素材时注意字母序（mp4 < wav），必须显式按优先级筛选扩展名

## P009 — Windows PowerShell 内联变量/执行策略/编码连环坑

**日期**：2026-09-28  
**分类**：环境  
**严重程度**：中（反复消耗工时，本任务内踩 4 次）

### 问题清单与规避
1. **内联命令中 `$_`/`$var` 被外层 shell 提前展开**（如 `ForEach-Object { $_.FullName }` 变成 `.FullName`）→ 规避：凡含 `$` 的 PowerShell 逻辑一律写成 `.ps1` 文件用 `-File` 执行，或改用 Grep/Glob/Python 等专用工具
2. **`npm`/`npx` 的 .ps1 入口被执行策略阻止** → 规避：用全路径 `& "F:\Program Files\nodejs\npm.cmd"`；npm 要在工作目录先有 package.json（无则 `npm init -y`）
3. **无 BOM 的 UTF-8 中文 .ps1 被 PowerShell 5.1 按 ANSI 解析，报“字符串缺少终止符”** → 规避：交付类脚本内容保持纯 ASCII（提示信息用英文）
4. PowerShell 无 `tail` → 用 `Select-Object -Last N`；`sorted(glob)` 类路径排序陷阱同 P008

### 规避建议
- Windows 上写任何供 Agent/用户执行的脚本，默认纯 ASCII + 不含内联 `$` 的一行命令；需要变量逻辑就落 .ps1 文件

## P010 — PG 下 INSERT 盲目追加 `RETURNING id` 致冷启动死循环

**日期**：2026-09-29  
**分类**：后端/DB  
**严重程度**：高（create_app 必崩，服务实际在跑更老代码）

### 问题描述
新代码上线后 `create_app()` 抛异常崩溃，credits 五表永远建不出来；但 `/api/health` 仍能响应，误以为“重启成功”。

### 错误现象
```
psycopg2.errors.UndefinedColumn: 字段 id 不存在
```
（出现在 `init_credits_tables` 建表 + 种子阶段）

### 根本原因
`db_adapter` 为回填 `lastrowid`，对**所有**未登记 `_PG_PK` 的表的 INSERT 一律追加 `RETURNING id`。而 system_config/user_credits/user_llm_config 等 TEXT 主键表**没有 id 列** → PG 报错 → 建表与种子同一事务整体回滚 → credits 表反复建不起来。health 能响应是因为一个更老的旧进程仍存活。

### 解决方式
`_needs_returning` 改为按 `information_schema.columns` 探测目标表是否真有 `id` 列，进程级缓存 `_pk_probe_cache`；未命中或探测异常保守返回 None（不回填）。验证：`CREATE_APP_OK`，重启后新代码（含积分拦截）真正生效。

### 规避建议
- SQLite→PG 适配层绝不可对任意 INSERT 盲注 `RETURNING`\；主键列名必须来自结构探测或显式登记表
- “health 返回 200”不等于新代码已加载；改动后重启需核对新代码独有行为（如新拦截错误码）是否真生效

## P011 — db_adapter 不转义 SQL 字面量内的 `%`

**日期**：2026-09-29  
**分类**：后端/DB  
**严重程度**：中

### 问题现象
直插/清理时 `... WHERE username LIKE 'p4chk_%'` 内联字面量报 `tuple index out of range`。

### 根本原因
adapter 把 `?` → `%s`，但**不转义 SQL 字符串字面量内部的 `%`**；psycopg2 将字面量里的 `%` 当占位符→参数元组越界。

### 解决方式 / 规避
LIKE 通配必须**参数化传入**（`conn.execute("... LIKE ?", ("p4chk_%",))`），不得把带 `%` 的模式写死在 SQL 文本里。

**复现（2026-09-28 积分测试）**：`tests/test_credits_system.py` 的 PG 清理用 `WHERE username LIKE 'crdt%'`（空参数+内联 `%`）同样中招，且被 `try/except: pass` 静默吞掉 → 残留 13 用户 + 共享配置 `credits_daily_bonus` 被留在测试值 0 未恢复。教训两条：① 清理/测试 SQL 里的 LIKE 模式一律参数绑定；② 数据清理与配置恢复要**各自独立 try**，且不能仅凭“测试 passed”判定干净——须**跑后查残留计数 = 0** 才算验收。

## P012 — 积分预检 402 拦截 HTTP 验收脚本（注册不登录→无每日赠分）

**日期**：2026-09-29  
**分类**：后端/测试  
**严重程度**：高（一次重启后 r10/p3 突然多个 FAIL）

### 问题现象
服务重启后新代码（积分 enforcement）真正生效，r10 1 FAIL / p3 7 FAIL，错误均为 `st=402 积分不足，请充值后继续使用`；pytest test_p5 test_07 skip。

### 根本原因
每日赠 100 分挂在 **login 钩子**（`grant_daily_bonus`），而各 HTTP 验收脚本 `register()` 拿到 register 返回的 token 就直接用，**从不 login** → balance 恒 0 → LLM 端点预检拦截。不是产品 bug（直连诊断确认新用户 login 后正常到账 100、precheck 放行）。

### 解决方式
修正测试口径（属测试数据准备，不动业务代码）：r10/p3/p2s/test_p5 的 `register()` 均改为“注册后再 login 一次拿 token”。修复后 r10 10/10、p3 20/20、pytest 100 passed（test_07 不再 skip）。

### 规避建议
- 日后凡是调 LLM/ASR 等计费端点的验收/回归脚本，新用户必须走 login（或显式预置积分），不能只用 register token
- 区分“产品回归”与“测试数据缺口”：402 先看登录链路是否触发赠分，再定修改代码还是改脚本

## P013 — C 盘清理静默杀掉 v2rayN 代理

**日期**：2026-09-29  
**分类**：环境  
**严重程度**：中（LLM 链路表面“超时/额度”，实则代理未运行）

### 问题现象
用户手动清理 C 盘临时文件后，LLM 相关用例出现 skip/失败，疑似网络问题。

### 根本原因

## P024 〔批5〕SPA 片段重注入 + 异步响应的双重竞态，令牌守卫成为固定模式

【2026-10-13】Windows 双绑定端口劫持复发（P006 同族坑二进宫）：重启服务后新路由 404，但同批新增的 9991 小服务却存活——矛盾现象的真相是 6001 上有**两个 LISTENING 进程**（旧代码进程 + 新进程各自绑 127.0.0.1:6001，Windows 下允许），请求被旧进程劫走。而“杀残留进程”脚本没杀掉旧的：netstat 行用正则 `:(6001|9991)\s` 匹配本地地址列，当端口恰好是**行尾最后一列**时后面没有空白，`\s` 永不命中 → pids 查出来是空集，误以为“无残留”。

**预防措施**：重启常驻服务的标准动作固化为四步：枚举端口全部 PID（行尾锚定正则）→ 逐个 kill → 复验 PORTS_CLEAN → 启动并探活新代码特征端点；探活不能只看主服务端口，多端口特性（如 6001+9991）要逐个验证。
