# 开发工作原则

> 本文档是 `AGENTS.md` 中开发规范的详细展开，Agent 在开发阶段必须遵循。

---

## 一、白盒测试（代码评审）

### 1.1 触发时机

每次代码修改完成后，**立即**发起白盒评审，不等用户要求。

### 1.2 评审方式

使用 Qoder 的 CodeReview 子代理（独立 Agent），评审范围：
- 本次 diff 涉及的所有文件
- 重点：逻辑漏洞、安全缺陷、架构违规、边界条件遗漏

### 1.3 评审循环

```
第1轮评审 → 修复问题 → 第2轮评审 → 修复 → 第3轮评审
                                         ↓
                              仍无问题 → 进入黑盒测试
                              有问题 → 修复后标记为"已尽力3轮，提请用户注意"
```

### 1.4 评审重点检查项

| 检查项 | 说明 |
|--------|------|
| 架构收敛 | 是否重复实现了已有公共函数？是否引入不必要的新依赖？ |
| 边界条件 | null/空字符串/超长输入/并发 等情况是否处理 |
| 安全 | 路径遍历、SQL注入、API Key 是否暴露在响应中 |
| 资源释放 | 数据库连接、文件句柄是否正确关闭 |
| 错误处理 | 异常是否被静默吞掉？错误响应格式是否统一？ |

## 二、黑盒测试（功能测试）

### 2.1 测试形式

**Python 后端**：
- 为每个 API 端点编写断言测试（pytest 或 unittest）
- 重点：正常路径 + 关键异常路径
- 测试文件命名：`test_<模块名>.py`，放在项目根目录

**前端功能**：
- 通过 `unified_logger.js` 在浏览器中埋点；前端所有调试/行为日志一律经 `/api/debug/log` 上报，最终落入后端 `logs/debug_trace.jsonl`（单一证据文件，前后端统一可时序对照）
- 常规回归仍优先用 HTTP/pytest；但**端到端功能测试必须采用脚本注入方式模拟真实用户操作**（浏览器注入 JS / CDP，调用页面真实函数链路，非直打接口代替），由用户 2026-09-28 指令确立

### 2.2 测试过程日志留痕（强制，用户 2026-09-28 指令）

**任何测试（单元/集成/接口/功能/E2E）的每一步都必须留可追溯记录，写入 `logs/debug_trace.jsonl`（或测试文档中逐条登记），内容包含：**
1. 本步做了什么（操作/用例名/输入）
2. 结果是什么（实际输出/断言结论）
3. 是否正确；不对则记录问题、根因、解决方案
4. 修正代码后重新测试，回归结果必须再次留痕

禁止“测了但没记录”；交付时测试记录与代码同PR可审阅。

### 2.3 时间控制

每个测试套件执行前，必须预估运行时间：

```
预估时间 = 测试用例数 × 单用例预估时间 + 启动开销
超时设置 = 预估时间 × 2
若超时 → 立即 kill → 分析是环境问题还是测试设计问题
```

### 2.4 环境健康保证

每次测试执行前：
1. 检查 Flask 服务是否运行（`Test-NetConnection localhost 5000`）
2. 检查数据库文件是否可访问
3. 确认没有残留进程

若环境不健康，先修复环境，再运行测试，不要盲目等待。

## 三、开发时间 vs 测试时间

### 3.1 基本比例

**同一功能**：`测试时间 ≤ 开发时间`

| 功能开发预估时间 | 测试时间上限 |
|----------------|------------|
| 10 分钟 | 10 分钟 |
| 30 分钟 | 30 分钟 |
| 1 小时 | 1 小时 |

### 3.2 超时处理

若测试超出时间上限：
1. 分析原因：是环境问题 or 功能设计问题？
2. 环境问题 → 修复环境，记录到掉坑笔记
3. 功能设计问题 → 告知用户，当前实现超出预期，是否调整方案
4. 禁止无限等待

## 四、命令执行时间控制

### 4.1 预估参考表

| 命令类型 | 正常耗时 | 超时设置 | 说明 |
|---------|---------|---------|------|
| `git status` / `git log` | < 5s | 30s | 快命令 |
| `git clone`（含代理处理）| 30-120s | 180s | 需处理代理问题 |
| `python app_flask.py` | 常驻 | - | 用 is_background=true |
| `pip install` | 视包大小 | 300s | 大包装前确认 |
| pytest（单文件） | < 30s | 60s | 超出则分析 |
| 读文件 / glob 搜索 | < 10s | 30s | 一般不超时 |
| 子代理审核 | 1-3 min | 5 min | 超时则跳过审核 |

### 4.2 超时 kill 后的处理

```
命令超时
  ↓
记录到掉坑笔记（哪个命令、预期多久、实际卡了多久）
  ↓
分析原因（环境问题 / 设计问题 / 代理问题）
  ↓
尝试替代方案（如：用异步、用后台执行、换命令写法）
```

## 五、Token 消耗管理

### 5.1 减少不必要消耗

- 读取大文件时，优先用行号范围，不要全文读取
- 文件修改用 SearchReplace，一次调用包含多个替换，不要拆成多次
- 子代理只在关键节点调用（方案评审、代码评审），不要频繁调用

### 5.2 消耗监控

Agent 应时刻意识到当前 token 消耗进度：
- 接近任务规划中的预算时，主动告知用户
- 若发现消耗超出预期，分析原因（是否走了弯路），调整策略

## 六、交付规范

### 6.1 交付前检查清单

```
□ 白盒评审（≥2轮）已通过
□ 黑盒测试通过率 100%
□ debug_trace.jsonl 中本次功能路径日志完整且符合预期
□ 开发日志已更新（业务变更用业务语言详述）
□ 若有业务规则变更，业务规则文档已同步更新
□ 掉坑笔记已记录本次遇到的新问题
```

### 6.2 交付时告知用户的内容

```
【交付说明】
功能：xxx
改动文件：xxx（用业务语言说明每个文件改了什么）
验收步骤：
  1. 打开 xxx 页面
  2. 点击 xxx 按钮
  3. 预期看到 xxx 结果
已知限制：xxx
下一步建议：xxx
```

## 七、统一调试日志使用规范

### 7.1 什么情况下必须写 debug 日志

| 场景 | 必须记录的内容 |
|------|--------------|
| API 端点被调用 | 端点名、请求参数摘要、结果状态 |
| LLM 被调用 | 提供商、prompt 长度、响应长度、耗时 |
| 数据库写操作 | 操作类型、影响行数 |
| 用户确认流程 | 用户选择（merge/new/skip） |
| 前端关键事件 | 按钮点击、API 响应、渲染完成 |

### 7.2 debug 日志格式

```json
{
  "timestamp": "2026-09-27T18:30:00",
  "source": "backend|frontend",
  "module": "api|knowledge|practice|llm|...",
  "action": "action_name",
  "status": "success|error|info",
  "data": {}
}
```

### 7.3 Agent 如何使用 debug 日志验证

测试完成后，执行：
```python
# 读取最后20条日志验证
import json
with open('logs/debug_trace.jsonl', 'r', encoding='utf-8') as f:
    lines = f.readlines()[-20:]
for line in lines:
    entry = json.loads(line)
    print(entry)
# 检查：1.功能路径是否完整 2.有无 error 状态 3.数据是否符合预期
```

## 八、MCP/外部工具调用频控（红线，2026-09-27 事故沉淀）

### 8.1 背景事故

上一轮工作中，browser-use MCP 调用过于频繁触发工具限额（流控），
整个执行过程被迫等待用户点击“继续”，工作中断——这是交付流程的严重倒退。

### 8.2 硬规则

1. **规划频率**：使用 MCP（browser-use 等）前先估算调用次数与间隔；
   连续交互类操作每次调用间隔≥数秒，单次任务链内 MCP 调用总数控制在必要最小范围。
2. **优先替代方案**：能用 HTTP 脚本（httpx/urllib）、pytest、CDP 直连脚本自证的，
   不用 MCP 点击。本轮验收即用 `server/tests/r9_acceptance.py`（纯 HTTP）+ pytest 完成。
3. **限流不卡死**：一旦观察到限流/需要用户点击“继续”，**立即停止该类调用**，
   切换到不受影响的工作（改代码/写文档/跑本地测试），绝不允许在同一入口上
   无限重试直到卡住。
4. **失败降级**：MCP 验证不可用时，降级为“代码层自证 + 用户实测步骤清单”，
   并在交付总结中如实说明哪部分未经真机验证及原因。
5. **产品约束同步**：页内调试面板/调试日志 UI 已全部删除（产品要求）；
   第七章的“统一调试日志”仅指 console + `logs/debug_trace.jsonl` 后端文件，
   不得再以页面浮层形式呈现。
