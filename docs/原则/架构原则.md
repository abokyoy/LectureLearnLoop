# 架构原则

> 第一原则：**架构收敛**，始终把收敛放在第一位。  
> 每次写新功能之前，先评估存量，再决定增量。

---

## 一、收敛第一

### 1.1 技术架构收敛

- 整个系统**只用一套 LLM 调用机制**（`llm_provider_factory.py` 工厂模式）
- 整个系统**只用一套数据库连接管理**（统一连接管理模块，不在各业务类中各自 `sqlite3.connect()`）
- 整个系统**只用一套日志/调试输出机制**（`logger_module.py` + `logs/debug_trace.jsonl`）
- 整个系统**只用一套配置加载方式**（`config.py` 的 `load_config()` / `save_config()`）

**禁止**：为同一类功能建立第二套实现。

### 1.2 程序架构收敛：公共函数注册制

每次新增一个可能复用的函数前，必须：

```
1. 查阅公共函数清单（下方）
2. 若已有近似功能 → 扩展现有函数，而非新建
3. 若确认是全新功能 → 在公共函数清单中登记，再实现
4. 实现后更新本文件的公共函数清单
```

**公共函数注册清单**（持续补充）：

| 函数 | 位置 | 职责 | 禁止重复 |
|------|------|------|---------|
| `load_config()` | `config.py` | 加载运行时配置 | 禁止在其他模块中重复读取 JSON 配置 |
| `save_config()` | `config.py` | 保存运行时配置 | 禁止在其他模块中直接写 `app_config.json` |
| `call_llm()` | `llm_provider_factory.py` | 统一 LLM 调用入口（含积分计费路由：预检/扣分/自备Key回落） | 禁止在业务代码中直接调 requests.post 访问 LLM API；计费只能通过此入口，不得另写扣分链路 |
| `start_llm_call()` | `llm_call_logger.py` | 开始记录 LLM 调用 | - |
| `end_llm_call()` | `llm_call_logger.py` | 结束记录 LLM 调用 | - |
| `debug_logger.log()` | `logger_module.py` | 写统一调试日志 | 禁止 print() 输出调试信息 |
| `UnifiedLogger` (前端) | `static/js/unified_logger.js` | 前端统一调试上报 | 禁止散落的 console.log 做正式调试 |
| `DatabaseManager.get_connection()` | `knowledge_management.py` | 知识管理系统 DB 连接 | - |
| `credits_service.*` | `credits_service.py` | 积分体系唯一出口：`charge_llm`/`charge_asr`/`precheck`/`get_balance`/`redeem_code`/`grant_daily_bonus`/`admin_adjust`/`billing_for_response`/`get_user_llm_config`/`effective_llm_config` | 禁止在任何端点/服务中直接写 `user_credits`/`credit_transactions`/`system_config`/`activation_codes` 表；一律走本模块 |
| `require_admin` | `auth.py` | 管理后台 API 鉴权装饰器（仅 is_admin=1） | 禁止在管理路由中手写权限判断 |

**注意**：`knowledge_management.py` 中 `KnowledgePointManager` 和 `ErrorQuestionManager` 各自实现了 LLM 调用（`_extract_with_deepseek` 等），这是历史遗留问题，应当逐步收敛到统一工厂。**新功能绝对不允许再添加类似实现。**

## 二、相似业务，相似实现

### 2.1 原则

对于**类似的业务逻辑**，必须用**同一种技术模式**实现：

| 业务类型 | 统一实现模式 | 说明 |
|---------|------------|------|
| LLM 调用 | 工厂模式 + 统一接口 | 所有提供商继承 `LLMProvider.call()` |
| 数据库 CRUD | 管理器类 + 连接复用 | 所有数据操作通过对应 Manager 类 |
| API 端点 | 统一响应格式 `{success, data/error}` | 所有 API 遵循相同格式 |
| 前端 API 调用 | `api.js` 封装的 API 模块 | 禁止直接 `fetch()` 调用 |
| 缓存型操作 | 先查缓存 → 无则计算 → 存缓存 → 返回 | 脑图、学习路径等均采用此模式 |
| 带降级的远程调用 | 主选 → 备选 → 兜底（**工厂层未实现，历史代码中有遗留手写降级链**） | `llm_provider_factory.py` 无自动降级，失败直接报错；`knowledge_management.py` 的 `_extract_with_deepseek` 中有历史降级链（DeepSeek→Gemini→Ollama→规则兜底），属应收敛对象 |

### 2.2 禁止"秀技术"

- 不要在同一个项目中混用多种实现风格
- 不要用不成熟的方案实现核心业务
- 不要引入新的库/框架，除非经过架构评审
- **当前最稳定成熟的架构模式**：Flask MVC + 服务层分离（见第三节）

## 三、MVC + 服务层架构

### 3.1 当前项目推荐架构层次

```
请求流向：
  浏览器（Jinja2 模板 + JS）
      ↓ Fetch API
  Flask 路由层（app_flask.py）
      ↓ 调用业务对象
  服务层（services/ + knowledge_management.py）
      ↓ 读写数据
  数据访问层（dal/ + DatabaseManager）
      ↓
  SQLite / 文件系统
```

### 3.2 各层职责边界

| 层次 | 职责 | 禁止做的事 |
|------|------|----------|
| 路由层 | 接收请求、参数校验、调用服务层、统一格式化响应 | 禁止在路由中写业务逻辑 |
| 服务层 | 业务规则实现、跨数据源协调 | 禁止直接操作 HTTP 请求/响应对象 |
| 数据访问层 | 单表/单源 CRUD | 禁止包含业务判断逻辑 |
| 前端模板层 | 页面渲染、用户交互、调用 API | 禁止包含复杂业务计算 |

### 3.3 新功能标准开发路径

```python
# 1. 数据访问层（dal/ 或 knowledge_management.py 的对应 Manager）
class SomeDAO:
    def get_by_id(self, id): ...
    def save(self, data): ...

# 2. 服务层（services/ 或 KnowledgeManagementSystem）
class SomeService:
    def do_business_logic(self, params):
        data = self.dao.get_by_id(...)
        # 业务规则处理
        return result

# 3. 路由层（app_flask.py）
@app.route('/api/some/endpoint', methods=['POST'])
def api_some_endpoint():
    data = request.get_json()
    # 参数校验
    result = some_service.do_business_logic(data)
    return jsonify({'success': True, 'data': result})

# 4. 前端 API 模块（api.js）
const SomeAPI = {
    async doSomething(params) {
        return api.post('/api/some/endpoint', params);
    }
}
```

## 四、禁止堆积式编程

### 4.1 识别堆积式编程的信号

以下任意一条出现，说明代码已经在堆积，需要停止并重构：

- 同一个文件超过 **500 行**（当前 `knowledge_management.py` 3192 行是严重违规）
- 同一个函数超过 **80 行**
- 复制粘贴超过 **10 行** 的代码块
- 新增函数与已有函数名相似但逻辑略有不同（说明应该合并）
- 一个类承担超过 **3 个不同职责**

### 4.2 精简标准

- **能一行写清楚的，不写三行**
- **能用内置函数的，不自己实现**
- **能参数化的，不写两个近似函数**
- **能复用工厂的，不在业务代码中重新调用 API**

### 4.3 当前已知待收敛的技术债

| 问题 | 优先级 | 收敛方向 |
|------|--------|---------|
| `knowledge_management.py` 中两套 LLM 调用实现 | 高 | 全部迁移到 `llm_provider_factory` |
| 两套练习数据库（`practice_history.db` / `practice_data.db`） | 中 | 合并为一个 |
| `app_qt.py`（3020行）+ `overlay_drag_corgi_app.py` | 中 | Flask 版本稳定后删除 |
| `base.html` 6064行（样式+逻辑混合） | 中 | 拆分为独立 CSS 文件 + 模块化 JS |
| 各模板中散落的 `console.log` | 低 | 统一替换为 `unified_logger.js` |

## 五、公共函数演进规则

### 5.1 新建公共函数的条件

同时满足以下两条，才能新建公共函数：
1. 在公共函数清单中确认没有近似实现
2. 此函数将在 **3 处以上**被调用（否则就地内联即可）

### 5.2 修改公共函数的规则

修改公共函数前必须：
1. 搜索所有调用方，评估影响范围
2. 经过 CodeReview 子代理评审
3. 运行所有调用方的相关测试
4. 在开发日志中记录修改原因和影响范围

### 5.3 公共函数命名规范

```python
# 数据访问：动词 + 对象 + by条件
get_knowledge_points_by_subject()
save_practice_record()

# 业务操作：动词 + 业务概念
extract_knowledge_points()
confirm_knowledge_points()

# 工具函数：动词 + 名词
load_config()
format_timestamp()
```
