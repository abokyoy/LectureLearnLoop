# 前端 UI 设计与验证工作原则

> 制定日期：2026-10-01（由用户下达）  
> 适用范围：所有 Web / Electron 界面的设计、改版、重构与验收。  
> 本原则与《开发工作原则》《架构原则》并列，是前端工作的最高执行标准。

---

## 一、设计阶段：必须借助 UI Skills，禁止凭空手写样式

1. 任何界面设计/改版任务，**必须调用已安装的 UI 技能**：
   - `ui-generator-skill`：产出生产级、极简现代 SaaS 质感的 UI 代码（Tailwind CSS + Shadcn UI 组件解构，禁止原生 CSS/行内样式/占位符代码）。
   - `ui-designer`：建立设计系统、视觉风格与可运行原型。
2. 本项目的设计基调定位：**现代化 SaaS 学习软件风格**——面向学生，简洁、明快、轻松、略带小可爱；拒绝"后台管理系统感"。
3. 样式引擎统一为 **Tailwind CSS**（本项目已通过 CDN 引入），组件规范对标 **Shadcn UI** 默认样式。

## 二、设计核对阶段：Stitch MCP 可用，注意调用频率

1. Stitch MCP 未加载进 IDE 的 MCP 列表，但**可直接通过 HTTP JSON-RPC 调用**（已验证通路）：
   - 端点：`https://stitch.googleapis.com/mcp`，Header：`X-Goog-Api-Key`（见 `.qoder/mcp.json`）
   - 协议：streamable HTTP，`initialize` → `tools/list` → `tools/call`，StatelessServer 无需维持 session
   - **必须走 V2RAYN 代理**（`http://127.0.0.1:10808`），PowerShell 5.1 需显式 `-Proxy` 参数（环境变量代理无效，已踩坑）
   - 探活/调用脚本模板：`server/tests/ui_probe.ps1`
2. 用于：生成设计稿、核对自建设计的可行性。
3. **频率纪律**：每日额度 400 次；单日优先复用已生成结果（落盘到 `design/` 目录）；调用失败不反复重试，降级为本地 Tailwind 手写并记入掉坑笔记。

## 三、验证阶段：截图识图反馈循环（核心新机制）

**禁止只靠 JS 点击与日志判断 UI 正确性。UI 的验证必须以"看得见"的证据为准。**

闭环流程（每个界面必须走完）：

```
① 设计（UI Skills 产出代码，必要时 Stitch 生成/核对设计稿）
② 运行（启动对应端，页面加载成功）
③ 截图（通过 browser-use MCP take_screenshot，或 Electron CDP :9222 截图）
④ 识图核对（当前 Agent 模型具备识图能力，直接 Read 截图文件比对设计意图；
   若未来模型不支持识图，切换最便宜的可视模型完成本步）
⑤ 判定：视觉不一致 → 修样式 → 回到 ③（直至一致）
⑥ UX 交互验证：用 browser-use 点击真实元素（按钮/表单/弹层），
   确认交互链路可用，而非仅 DOM 存在
⑦ 全部通过 → 该界面闭环，进入下一个界面
```

要点：
1. 元素必须**在 UI 上真实可见**（截图里看得见），再谈交互。
2. 每轮截图后要**自我审视间距、配色、层级**，至少修正一遍再交付。
3. Electron 端界面（悬浮窗 overlay、主面板）通过 `start_app.ps1 -Dev` 启动 CDP :9222 后截图验证。

## 四、时间与卡住纪律（继承最高原则）

1. 每次界面设计/验证子任务，**先规定时间**（估算写入任务拆解），设置 timeout。
2. 超时后归因：
   - **正常耗时**（页面确实复杂）→ 继续做；
   - **异常卡住**（网络/进程/渲染死锁）→ 立即 kill + 绕过（换端口、换截图方式、脚本落盘读结果），**禁止无限期卡在单一任务上**。
3. 同一入口连续两次失败，禁止第三次盲试，必须换机制。

## 五、走查与重设计纪律

1. 全界面改版必须先**列清单、排计划**（按页面逐个走查），再从头到尾执行，禁止东改一块西改一块。
2. 设计系统先行：色板、字阶、圆角、间距、组件规范先定稿（DESIGN 约定一份基准），所有界面套用同一套，保证全局一致。
3. 每个界面重设计完成后，截图存档（改造前/后对比），写入开发日志。
