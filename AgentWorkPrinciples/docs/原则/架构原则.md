# 架构原则

> 第一原则：**架构收敛**，始终把收敛放在第一位。
> 每次写新功能之前，先评估存量，再决定增量。
> 通用模板版：公共函数清单与技术债表初始为空，随项目开发逐步登记。

---

## 一、收敛第一

### 1.1 技术架构收敛

同一类系统级能力，**全项目只允许一套实现**：

| 能力类别 | 收敛要求 |
|---------|---------|
| 外部 AI/LLM 调用 | 只用一套调用机制（统一工厂/入口） |
| 数据库连接管理 | 只用一套连接管理模块，禁止在各业务类中各自建连 |
| 日志/调试输出 | 只用一套机制，最终落入统一调试日志文件 |
| 运行时配置加载 | 只用一套读写入口，禁止散落直接读写配置文件 |
| 前端 API 调用 | 只用一层统一封装，禁止散落 fetch/裸请求 |

**禁止**：为同一类功能建立第二套实现。

### 1.2 程序架构收敛：公共函数注册制

每次新增一个可能复用的函数前，必须：

```
1. 查阅公共函数清单（下方）
2. 若已有近似功能 → 扩展现有函数，而非新建
3. 若确认是全新功能 → 在公共函数清单中登记，再实现
4. 实现后更新本文件的公共函数清单
```

## 二、相似业务，相似实现

### 2.1 原则

对于**类似的业务逻辑**，必须用**同一种技术模式**实现：

| 业务类型 | 统一实现模式 | 说明 |
|---------|------------|------|
| 外部服务调用 | 工厂模式 + 统一接口 | 所有提供商继承同一基类接口 |
| 数据库 CRUD | 管理器类 + 连接复用 | 所有数据操作通过对应 Manager/DAO 类 |
| API 端点 | 统一响应格式 `{success, data/error}` | 所有 API 遵循相同格式 |
| 缓存型操作 | 先查缓存 → 无则计算 → 存缓存 → 返回 | 所有可重复生成的重计算均采用此模式 |
| 带降级的远程调用 | 主选 → 备选 → 兜底，统一在工厂层实现 | 禁止在业务代码中手写各自的降级链 |

### 2.2 禁止"秀技术"

- 不要在同一个项目中混用多种实现风格
- 不要用不成熟的方案实现核心业务
- 不要引入新的库/框架，除非经过架构评审
- 新项目立项时确定**一种最成熟稳定的架构模式**并全项目沿用（如 MVC + 服务层分离，见第三节）

## 三、分层架构参考（MVC + 服务层）

### 3.1 推荐架构层次（语言/框架无关）

```
请求流向：
  客户端（浏览器 / 桌面端 / 移动端）
      ↓ HTTP API
  路由层（接收请求、参数校验、统一响应格式化）
      ↓ 调用业务对象
  服务层（业务规则实现、跨数据源协调）
      ↓ 读写数据
  数据访问层（单表/单源 CRUD）
      ↓
  数据库 / 文件系统
```

### 3.2 各层职责边界

| 层次 | 职责 | 禁止做的事 |
|------|------|----------|
| 路由层 | 接收请求、参数校验、调用服务层、统一格式化响应 | 禁止在路由中写业务逻辑 |
| 服务层 | 业务规则实现、跨数据源协调 | 禁止直接操作 HTTP 请求/响应对象 |
| 数据访问层 | 单表/单源 CRUD | 禁止包含业务判断逻辑 |
| 前端模板层 | 页面渲染、用户交互、调用 API | 禁止包含复杂业务计算 |

### 3.3 新功能标准开发路径

```
1. 数据访问层：DAO/Manager 提供 get_by_id / save 等基本操作
2. 服务层：Service 类组合 DAO，实现业务规则
3. 路由层：端点做参数校验 → 调服务 → 返回统一格式 {success, data/error}
4. 前端：通过统一封装的 API 模块调用，不裸发请求
```

## 四、禁止堆积式编程

### 4.1 识别堆积式编程的信号

以下任意一条出现，说明代码已经在堆积，需要停止并重构：

- 同一个文件超过 **500 行**
- 同一个函数超过 **80 行**
- 复制粘贴超过 **10 行** 的代码块
- 新增函数与已有函数名相似但逻辑略有不同（说明应该合并）
- 一个类承担超过 **3 个不同职责**

### 4.2 精简标准

- **能一行写清楚的，不写三行**
- **能用内置函数的，不自己实现**
- **能参数化的，不写两个近似函数**
- **能复用工厂/公共入口的，不在业务代码中重新调用外部 API**

## 五、公共函数演进规则

### 5.1 新建公共函数的条件

同时满足以下两条，才能新建公共函数：
1. 在公共函数清单中确认没有近似实现
2. 此函数将在 **3 处以上**被调用（否则就地内联即可）

### 5.2 修改公共函数的规则

修改公共函数前必须：
1. 搜索所有调用方，评估影响范围
2. 经过 CodeReview 子代理评审
3. 运行所有调用方的相关测试
4. 在开发日志中记录修改原因和影响范围

### 5.3 公共函数命名规范

```
# 数据访问：动词 + 对象 + by条件
get_items_by_condition()
save_record()

# 业务操作：动词 + 业务概念
extract_knowledge_points()
confirm_merge()

# 工具函数：动词 + 名词
load_config()
format_timestamp()
```
