# 多端架构原则

> 适用于一个后端服务 + 多个客户端（Web / 桌面端 / 移动端）的项目。
> 核心约束：**所有端共享同一后端 API，禁止各端自行实现业务逻辑。**
> 通用模板版：新项目启动时先按本节模板填写"功能边界划分表"，再开始开发。

---

## 一、功能边界划分（模板，新项目立项时与用户共同填写）

### 1.1 划分原则

- **主端（通常为 Web 端）**：承载完整业务闭环，复杂交互功能全部在这里
- **轻量端（移动端/桌面端/小程序等）**：定位明确、只做核心场景（如采集、速查），不做复杂操作
- 每个功能属于哪一端，**立项时逐条与用户确认并登记**，开发中不得随意跨端复制功能

### 1.2 登记模板

```
主端功能清单（完整闭环）：
✅ （逐条登记）

轻量端功能清单（核心场景）：
✅ （逐条登记）
❌ 明确不做的功能（及原因）：
❌ （逐条登记）

共享层（后端统一提供，各端只调 API）：
✅ 外部服务调用（同一工厂入口）
✅ 数据存取（同一数据库/文件存储）
✅ 用户配置（统一配置读写接口）
```

---

## 二、技术选型约束

### 2.1 选型纪律

1. 主端技术栈立项时确定后，**全项目沿用，不引入第二套**
2. 轻量端候选方案（PWA / Flutter / React Native / 小程序 / Electron 等）列优缺点对比表后，**必须与用户确认后再选型，Agent 不得自行决定**
3. 未与用户确认前，不引入新框架（React、Vue、Next.js 等偏离既定栈的选择）

### 2.2 禁止事项

- 不为任何端单独实现一套业务逻辑（端只调用 API，不直连数据库）
- 不在轻量端本地存储核心业务数据（数据源永远在后端）
- 不在一端能完成的功能，第二端再重写一遍实现

---

## 三、API 设计原则（多端共享）

### 3.1 统一 API 契约

各端使用同一套 RESTful API，可按前缀区分端（如 `/api/*` 与 `/api/mobile/*`），但**业务逻辑同一、响应结构同一**：

```
1. 所有响应统一格式：
   成功: {"success": true, "data": {...}}
   失败: {"success": false, "error": "错误描述"}

2. 分页统一参数：?limit=N&offset=M
   响应统一包含: {"items": [...], "total": N}

3. 文件上传统一用 multipart/form-data，其他用 JSON

4. 认证升级路径预先约定（如 Header Bearer Token），不破坏 URL 结构
```

### 3.2 端特有 API 登记

轻量端特有的能力需求（如上传录音、拍照 OCR）逐项登记为待实现 API 清单，标注优先级；未实现的 API 不得用端侧本地逻辑顶替。

---

## 四、数据同步原则

多端共享后端数据时：

1. **唯一数据源**：文件/数据库是唯一真相源，各端都通过 API 读写
2. **并发写入评估**：所用数据库是否支持多进程并发写入须先确认；若不能并发，明确约定写入时序（如移动写时 Web 只读）
3. **调试日志归一**：各端日志都写入同一 `logs/debug_trace.jsonl`，通过 `source` 字段区分端（`web` / `mobile` / `desktop`）

---

## 五、轻量端开发规则

1. **不自行决定技术选型**，必须先向用户确认方案（多方案对比后由用户裁定）
2. **不重复实现后端业务逻辑**，端只调用 API
3. **UI 优先**：交互设计符合该端操作习惯（手机端：单手操作、大按钮）
4. **离线能力**：采集类操作（拍照/录音）断网时暂存本地，有网时自动上传
